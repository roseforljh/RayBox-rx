# RX 稳定性、缓存与连接选择验证（2026-10-31 UTC）

本轮按“先稳定、再内存、再连接成功率”的顺序修改现有 RX。源码和独立 Linux 实验内核已验证；没有替换生产服务，没有提交或推送，也没有打 Android AAR。本轮没有把 OOB 原型合入应用。

## 解决的问题

1. **数据明明还没传完，控制探测失败却拖住恢复。** 并发 RX 现在继续依据先前已确认的待交付数据检测和修复停滞；没有数据待传时仍保留正常空闲语义。新增故障测试在旧代码下无法按时完成，修复后完整交付。
2. **已经取消，还在等拨号。** 握手竞速直接响应调用方取消；落败、失败和取消后迟到的成功连接都会关闭。移除了专门等待迟到结果的清理 goroutine。无法强制终止不理会 context 的自定义拨号器内部代码，但它不会继续阻塞调用方，迟到连接也不会被遗留。
3. **小连接一上来就占满大缓存。** 服务端回放缓存改为按需增长，最高仍受 `maxReplayBytes` 限制；全部 ACK 后释放缓存引用。保留偏移、反压和未 ACK 数据，不靠丢数据省内存。释放引用不等于操作系统立即收回 RSS。
4. **某一段卡住，客户端把整个大窗口都提前堆满。** 预取队列上限改为 `min(window / segment, 2*N)`，包括已完成但未消费的任务；最后一段按实际大小分配。关闭且 worker 退出后释放队列引用。N16、64KiB段时，任务数据上限约2MiB，HTTP等其他内存另计。
5. **控制、上传换 client 后又忘记哪个入口不好用。** 数据池、控制和上传共享所属缓存 HTTP client 的健康记录，复用它的后续会话也可沿用。连续失败两次后短暂冷却，约1秒起、最多30秒；成功清除，过期可再试。全部冷却时仍尝试最早恢复者。调用方主动取消或别的竞速获胜造成的拨号取消不计失败。这是进程内记录，不是跨网络持久化策略。
6. **选择 H1，Chrome 指纹却实际协商成 H2。** 本地真实 TLS 测试已复现该问题。现在让指纹的 ALPN 与选定 HTTP transport 一致，清理不适用的 ALPS，显式握手后核对协议；普通非 RX、非指纹的原生 TLS 保留原来的惰性握手。证书验证仍执行，ECH 外层按既有语义处理；没有宣称已在公网 ECH 路径验收。

协议、认证、ACK边界和默认参数未改变。修改位于 `transport/internet/splithttp/` 的客户端、回放缓存、并发和预连接文件，以及 `transport/internet/tls/tls.go`；对应测试一并补充。没有新增依赖。

## 本地验证

工具链为 Go 1.27.3，使用本地依赖缓存。

```text
go test -race ./transport/internet/splithttp ./transport/internet/tls ./infra/conf \
  -run 'RX|FingerprintHonorsALPN|TLS|ECH' -count=1 -timeout 120s
```

通过192个测试及子测试；splithttp 6.584秒、tls 13.274秒、infra/conf 1.116秒。另在 sing-box 模块执行 `go test ./protocol/xray -count=1 -timeout 120s`，通过。上述是相关范围验证，不是全仓测试。

缓存小会话微基准（16MiB上限、实际写入1KiB后ACK）由约16,777,906 B/op降至4,624 B/op，只说明缓存分配变化，不能换算成整机内存降幅或用户容量。

独立 Linux amd64 内核构建成功，大小32,252,028字节，SHA-256：

```text
da0525cecdb31b0ee41a671ffcf4e5abc22acafc7a15b89db8a6d76bfdc5704a
```

冻结源码manifest的SHA-256为 `515963483a6006547fcba7dcc0b179cef34a37e3e7a45581e2efcdbdbc62e608`。原始测试JSONL、manifest和实验记录保存在被Git忽略的 `artifacts/stability-20261031/`。配置和原始抓包含私有资料，不随报告发布。

## RU → CF → UK 的缓存对比

两台既有自有服务器，13个既有CF入口；没有扫描或扩池。使用HTTP/80、VLESS正文认证加密、RX v2控制认证加密，固定64KiB段、并发16。本轮三档均为同一新版内核，只改变回放窗口。每档仅一个应用下载请求，进程独立启动，RSS为代理进程采样峰值，其他服务和内核内存未计入。

| 回放窗口 | 完整下载及SHA-256 | 含启动耗时 | UK服务端峰值RSS | RU客户端峰值RSS | 段重试 |
|---|---|---:|---:|---:|---:|
| 16MiB | 64MiB，通过 | 68.222秒 | 73.50MiB | 37.05MiB | 2 |
| 1MiB | 64MiB，通过 | 112.846秒 | 39.57MiB | 38.25MiB | 4 |
| 2MiB | 64MiB，通过 | 63.529秒 | 43.31MiB | 38.39MiB | 0 |

三档下载SHA-256均为：

```text
55930abe0d7fa6b891e7897127fc663277b98357f1d75b15849f01af38900a82
```

本场景优先采用 **2MiB回放窗口**：服务端采样峰值比16MiB档低约41%，本次耗时没有恶化。1MiB已等于16个64KiB段的最低协商容量，虽然能正确滚动传完64MiB，却多了明显等待，不作为本场景首选。所有结果仅各一次，受时段和网络波动影响；这不是新旧源码A/B，也不证明客户端内存下降或速度提升。

历史“小窗口小于文件就会卡死”的现象没有在本轮三个64MiB样本中复现。缓存需要保住的是未确认数据，不需要与整文件一样大；这不代表任何小窗口或线路都已经验收。未修改通用默认值，不能把本场景配置直接推广到原TLS受限路径。

## 2MiB窗口持续传输

随后沿同一路径，以1GiB源文件做一次三分钟观察，curl截止183秒，整档上限185秒，SYN预算6000；固定窗口2MiB、段64KiB、并发16。

- 含启动共183.323秒，收到190,128,128字节，即181.320MiB。5秒采样间隔内持续有数据推进，段重试与上传重试均为0，唯一SYN共3054，未触及SYN预算。
- UK源文件相同长度前缀、RU落盘前缀和接收过程流式SHA-256三者一致：`9768128bbd6aa3818e08a20adb3064763251d2075673535cd6c25e2c83f605df`。
- UK代理峰值RSS为40.98MiB，RU客户端40.26MiB。UK的第1、2、3分钟RSS中位数分别40.41、40.48、40.61MiB，没有随累计下载量同幅增长；三分钟不能排除慢速泄漏或证明长期稳定。
- curl按预设时限退出28，`complete_and_hash_match=false`。这是收到前缀的完整性验证，**没有完整下载1GiB，也不作为整文件通过**。

本场景可在两端既有的、安全配置完整的 `rx` 对象中采用 `maxReplayBytes=2097152`、`maxResponseBytes=65536`、`maxConcurrentSegments=16`。这些是本次HTTP/80路径的候选参数，仍须保留已有 `authKey`、VLESS正文认证加密、会话和重试预算，不构成可独立使用的完整配置。

## 实验管理与边界

原父脚本在第二档完成后遇到本地日志重名，未启动原计划的长测。已保留两档结果、补收1MiB证据、确认两端清理，再用独立runner执行2MiB测试。脚本问题没有被计为网络失败。

各档结束后均停止实验服务。最终独立只读审计确认两端临时unit、进程和持有实验路径的文件句柄均为0，实验监听端口空闲，清理错误列表为空。UK生产监听2053/443/8443及其PID795/799/797、RU生产443/8443及其PID25368均保持。远端仅保留已停止的私有实验文件，没有改动生产配置。

本轮没有量化连接成功率提升百分比，没有Android实机、多用户容量、跨运营商、整夜运行或完整1GiB的验收结果。地址冷却和协议匹配的收益有本地行为测试支撑，不能由单个成功下载推断全网成功率。
